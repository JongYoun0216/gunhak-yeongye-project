## 1. 프로젝트 한눈에 보기

### 프로젝트 목적

**호국실록**은 장병들이 팀을 구성해 지역의 안보·보훈 거점을 직접 이동하면서 미션을 수행하고, 그 수행 기록을 하나의 '역사/실록'으로 남기는 **GPS + Web-AR + AI 기반 지역 탐험형 팀빌딩 게임**이다.

제안서가 제시하는 핵심은 다음과 같다.

- GPS를 이용한 거점 탐색
- 팀 내 역할 분담
- Web-AR을 이용한 유물/대상 스캔
- OCR/NLP를 이용한 암호·퀴즈 검증
- Vision AI를 이용한 경례/대형/포즈 검증
- AI Game Master를 통한 실시간 관제와 힌트
- 시간·점수·페널티를 포함한 게임 엔진
- 최종 점수/순위 및 미션 수행 기록 정산
- 지역 상권·문화시설과 연결되는 보너스 미션
- AI를 활용한 지역/부대별 시나리오 자동 생성

제안서에서는 별도 앱 설치 없이 **QR → 모바일 Web/PWA** 방식으로 접속하는 것을 핵심 UX로 잡고 있다. fileciteturn0file0L21-L35

# 2. 핵심 기능 전체 목록

## A. 게임 시작 / 팀 구성

### A-1. QR 기반 게임 입장

**제안서 요구사항**
- 현장 QR 코드 스캔
- 앱 설치 없이 모바일 웹 접속
- PWA 방식
- 목표는 현장에서 빠르게 접속하는 Zero-Barrier UX

**구현해야 할 것**
- QR 코드 생성 및 게임 URL 연결
- `/game/{gameId}` 같은 게임 세션 URL
- 모바일 브라우저 대응
- PWA manifest
- Service Worker
- 카메라/GPS 권한 요청
- 팀 코드 또는 참가 코드 입력
- 게임 세션에 참가자 연결

**오픈소스**
- `html5-qrcode`: 웹에서 QR/바코드 카메라 스캔 가능
- 일반 PWA는 브라우저 Web API + Service Worker로 구현 가능
- Workbox를 사용하면 Service Worker 관리가 편해짐

참고:
- https://github.com/IL-Internet/html5-qrcode

### A-1-1. PDF 기획서에 명시된 비기능 요구사항 (기존 문서에 누락되어 있던 부분)

PDF 기획서 6페이지("QR코드 스캔으로 시작하는 웹 기반 AR 임무")에는 아래 두 가지 구체적 목표치가 제시되어 있는데, 초안에는 반영되어 있지 않았다.

- **3초 이내 접속**: QR 스캔 후 게임 화면 렌더링까지 3초 이내를 목표로 한다. PWA 초기 로드 시 번들 크기 최소화, 코드 스플리팅, 지도/AR 등 무거운 모듈의 지연 로딩(lazy loading)이 필요하다.
- **군 특수 단말기 100% 호환**: 부대에서 지급하는 특수/구형 단말기·브라우저 환경에서도 100% 구동을 목표로 한다는 요구사항이 있다. 이는 다음을 의미한다.
  - 최신 브라우저 API(WebAR용 WebGL, MediaPipe WASM 등)를 사용하기 전에 **군 지급 단말기의 실제 OS/브라우저 버전 확인이 선행되어야** 한다.
  - 구형 Android WebView 등에서는 WebAR·Pose 추정이 정상 동작하지 않을 수 있으므로, 해당 기능이 불가능한 단말기에서는 **폴백(fallback) 경로**(예: 사진 촬영 후 서버 측 검증으로 대체)를 마련해야 한다.
  - 이 요구사항은 오픈소스만으로 보장되지 않는, **프로젝트 고유의 호환성 검증/QA 작업**이다.

## B. 팀 / 역할 관리

### B-1. 팀 생성 및 참가

제안서에는 소부대 단위 팀을 구성하고 역할을 명확히 나누는 구조가 제시되어 있다.

**역할 (4대 전술 클래스)**
1. Command / 지휘관 — 팀 동선 통솔 및 작전 최종 결정, 단체 구호 지휘
2. Scout / 정찰원 — GPS 단말 탐지, 최단거리 이동 경로 확보 및 위험 구역 회피
3. Radio / 통신원 — AI 통제관 실시간 교신, 현장 데이터 및 사진 전송
4. Crypto / 암호해독관 — 현장 비문 해독, 역사 퀴즈 논리 분석 및 시스템 정답 입력

> PDF 기획서(5페이지)에는 4개 클래스 모두 영문명(Command/Scout/Radio/Crypto)이 부여되어 있다. 역할 배정 UI·DB 스키마에서도 한글명이 아닌 영문 클래스 코드를 기본 키로 사용하는 것이 확장(다국어 지원, 신규 테마 부대 적용)에 유리하다.

**구현해야 할 것**
- 팀 생성
- 팀원 초대/참가
- 역할 배정
- 역할별 권한
- 현재 팀원 상태
- 팀 전체 진행률
- 역할별 미션 수행 여부 기록

### B-2. 역할 기반 미션

예:
- 지휘관: 이동/작전 결정, 구호 통솔
- 정찰원: GPS 탐지 및 이동 경로 확보
- 통신원: AI 통제관과 교신
- 암호해독관: 퀴즈/암호 미션 수행

**중요**
단순히 UI에 역할 이름만 보여주는 것이 아니라 **역할별 행동을 실제 점수/미션 조건과 연결하는 게임 로직**이 필요하다.

# 3. GPS / 지도 / 거점 시스템

## C-1. 실시간 GPS 위치

**제안서 요구사항**
- 참가자의 GPS 위치 확인
- 거점까지 이동
- 안전 구역 이탈 감지
- 최적 이동 경로 안내

제안서에서는 거점 반경 **15m 내 진입**을 거점 도착 조건으로 예시하고 있다. fileciteturn0file0L38-L45

**구현**
- `navigator.geolocation.watchPosition()`
- 현재 위도/경도 저장
- GPS 정확도(`accuracy`) 확인
- 서버에 위치 주기 전송
- 지도 위 현재 위치 표시
- 거점 위치 표시
- 도착 판정

### C-2. Geofencing

핵심 로직:

```text
현재 위치
    ↓
거점 좌표와 거리 계산
    ↓
거리 <= 15m?
    ├─ YES → 거점 도착 처리
    └─ NO  → 계속 이동
```

또한 안전 구역 이탈 시 경보를 발생시키는 기능이 필요하다.

PDF 기획서 7페이지에 따르면 안전 구역 이탈 시 단순 경보 알림뿐 아니라 **경로 리디렉션(현재 위치 기준 올바른 경로 재탐색·재안내)** 까지 자동으로 트리거되어야 한다. 즉 이탈 감지 → 알림 발송 → (C-4의 경로 안내 로직 재호출) → 갱신된 경로를 지도에 즉시 반영, 의 흐름으로 Geofence Engine과 경로 안내(C-4) 모듈이 연동되어야 하며, 초안에는 이 연동 관계가 명시되어 있지 않았다.

**구현 난점**
GPS는 건물/도심 환경에서 오차가 발생하므로 단순히 `distance < 15m` 하나만으로 판정하면 오작동할 수 있다.

따라서:

- GPS accuracy 확인
- 일정 시간 연속으로 반경 내인지 확인
- 위치 튀김 제거
- 여러 GPS 샘플 평균
- 서버 측 최종 판정

등이 필요하다.

제안서에서는 거점 간 거리와 상황에 따라 도보/대중교통 이동을 안내한다. fileciteturn0file0L83-L90

```text
오른손 손목이 오른쪽 관자놀이 부근
+
팔꿈치 각도 범위
+
상체 방향
+
사람 수 >= N
```

같은 규칙 기반 판정 또는 별도의 분류 모델이 필요하다.

### G-1-1. 기획서에 명시된 판정 통과 기준 (초안 누락분)

PDF 기획서 7페이지("자동 미션 검증 엔진 (Vision AI)")에는 **"인원수 판독 및 자세 정확도 85% 이상 시 통과"**라는 구체적 임계값이 명시되어 있다. 초안에는 이 수치가 반영되어 있지 않았다. 구현 시 다음이 필요하다.

- 자세 정확도를 0~100% 스코어로 환산하는 채점 함수(예: 목표 관절 각도 대비 오차율 역산) 설계
- 85%라는 기준값을 하드코딩하지 않고 **거점/미션별로 조정 가능한 설정값(config)** 으로 관리 — 현장 테스트 결과에 따라 조정될 가능성이 높음
- 85% 미만일 때는 실패로 처리되어 §10의 힌트/페널티 단계(1회 실패 카운트)로 이어지는 연동 로직 필요

```text
                  ┌─ GPS
```

AI는 이런 상태를 바탕으로 자연어 안내를 만드는 역할을 담당한다.

## 14-1. 전국 확장 테마 및 비즈니스 모델 루프 (초안에 누락되어 있던 부분)

PDF 기획서 11페이지("월드 맵 확장성 및 지역 상권 연계 비즈니스 모델")는 단순 지역 체험 기능을 넘어, 이 프로젝트가 **광주 외 전국 단위로 확장되는 로드맵**과 **반복 가능한 비즈니스 순환 구조**를 핵심 차별점으로 제시한다. 초안에는 이 두 가지가 전혀 반영되어 있지 않아 보완한다.

### 전국 4대 전술 테마 (거점 도시별 시나리오)

| 지역 | 테마 |
|---|---|
| 인천 | 상륙작전 레이스 |
| 통영·한산도 | 삼도수군통제사 작전 |
| 파주 | DMZ 평화 탐험 |
| 안동 | 임청각 군자금 수송 |

이는 §16(AI 콘텐츠 자동 생성)에서 다루는 "지역/부대별 시나리오 자동 생성" 기능이 실제로 커버해야 하는 목표 범위이기도 하다. 즉 시나리오 생성기는 광주 한 지역만이 아니라, 위 4개 테마처럼 **지역별 역사적 소재와 미션 타입을 결합해 재사용 가능한 형태**로 설계되어야 한다. 구현 관점에서는 다음이 필요하다.

- 거점(Waypoint)·미션(Mission) 테이블을 **지역(region) 단위로 네임스페이스 분리**하여 여러 지역 게임을 동시 운영 가능하게 설계
- 시나리오 템플릿을 "역사적 배경 + 거점 유형 + 미션 유형"의 조합으로 파라미터화하여, 신규 지역 추가 시 콘텐츠 제작 리드타임을 줄이는 구조

### 비즈니스 모델 순환 구조

기획서는 다음과 같은 4단계 순환(loop) 다이어그램을 제시한다.

```text
부대 작전 수행 → 지역 경제 활성화 및 장병 복지 증진
     ↑                                      │
     │                                      ↓
전통시장 방문(호국 양식) ← 전술 바우처/쿠폰 결제
```

이는 §14의 "지역 체험/상권 연계"가 일회성 이벤트가 아니라 **게임 운영 사이클마다 반복되는 순환 구조**로 설계되어야 함을 뜻한다. 즉:

- 작전 수행(게임 플레이) 종료 시 자동으로 전술 바우처가 발급되고,
- 바우처는 실제 결제(전통시장 등)로 이어지며,
- 이 소비 데이터가 다시 "지역 경제 활성화 및 장병 복지 증진" 지표로 집계되어 다음 게임 운영·부대 유치의 근거 자료가 되는 흐름까지 데이터 모델에 포함되어야 한다.
- MVP 단계에서는 결제 연동 없이 "쿠폰 발급 → 사용 여부(redeemed) → 집계 리포트"까지만 구현하고, 결제/정산은 이후 단계로 분리하는 것이 현실적이다(§14 주의사항과 동일한 이유).

# 23. 무엇을 '직접 만들어야 하는가'

이 프로젝트에서 오픈소스를 가져온다고 해서 완성되는 것은 아니다.

실제 핵심 개발 대상은 다음이다.

## ① Game Engine

가장 중요하다.

```text
게임 시작
→ 거점 이동
→ 도착
→ 미션 오픈
→ 시도
→ 검증
→ 성공/실패
→ 힌트
→ 점수
→ 다음 거점
→ 종료
```

이 전체 상태를 관리해야 한다.

---

## ② Mission Engine

각 미션 타입을 하나의 공통 인터페이스로 만드는 것이 중요하다.

예:

```python
class MissionValidator:
    def validate(self, submission):
        ...
```

구현체:

```text
QuizValidator
OCRValidator
ARValidator
PoseValidator
PhotoValidator
LocationValidator
```

---

## ③ Scoring Engine

모든 점수 계산을 한곳에서 관리해야 한다.

```text
Mission Score
+ Bonus
+ Time Bonus
+ Teamwork
+ No-Hint Bonus
- Hint Penalty
- Time Penalty
```

---

## ④ Geofence Engine

GPS와 미션을 연결한다.

```text
GPS
 ↓
거리 계산
 ↓
정확도 확인
 ↓
연속 위치 확인
 ↓
도착 판정
 ↓
Mission Unlock
```

---

## ⑤ AI Verification Layer

AI별로 검증기를 분리한다.

```text
OCR Validator
NLP Validator
AR Validator
Pose Validator
```

이렇게 만들어야 나중에 AI 모델을 교체하기 쉽다.

# 34. 결론

이 프로젝트를 한 문장으로 정리하면:

> **"GPS로 실제 지역을 이동하고, 각 거점에서 OCR·NLP·WebAR·Vision AI를 이용해 미션을 수행하며, Backend의 게임 엔진이 시간·점수·힌트·팀 상태를 실시간 관리하고, 마지막에는 모든 수행 기록을 디지털 실록으로 보여주는 Web 기반 팀빌딩 게임"**이다.

핵심은 AI 모델 자체보다 **Game Engine + GPS/Geofence + Mission Engine + AI Validator + Score Engine**을 하나의 흐름으로 연결하는 것이다.

오픈소스를 적극 활용하면 OCR, 지도, Routing, AR, Pose, QR, 3D 렌더링 같은 저수준 기술을 처음부터 만들 필요는 없다. 반면 **'어떤 조건에서 미션을 성공으로 인정할 것인지', '언제 힌트를 주고 얼마를 차감할지', 'GPS 도착을 어떻게 확정할지', 'AI 결과를 어떻게 점수에 반영할지'는 프로젝트 고유 로직이므로 직접 개발해야 한다.**

따라서 개발의 중심은 다음과 같이 잡는 것이 좋다.

```text
                 ┌──────────────┐
                 │   Game Engine │
                 └──────┬───────┘
                        │
        ┌───────────────┼────────────────┐
        ↓               ↓                ↓
      GPS           Mission           Score
    Geofence         Engine           Engine
        │               │                │
        │       ┌───────┼───────┐        │
        │       ↓       ↓       ↓        │
        │      OCR     AR      Pose      │
        │       │       │       │        │
        └───────┴───────┴───────┴────────┘
                        │
                        ↓
                 AI Game Master
                        │
                        ↓
                 Final De-briefing
                        │
                        ↓
                  Digital History
```
